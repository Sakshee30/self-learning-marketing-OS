# GrowthOS CMS Studio Implementation Coverage Ledger

Updated: 24 September 2026

This ledger covers the initial `cms-studio/` foundation. It is intentionally narrower than the complete Marketing Studio architecture and does not claim that public release orchestration, media processing, blog operations, or website rendering are complete.

## Implemented in this batch

- Separate Payload CMS + Next.js application boundary backed by PostgreSQL.
- Authenticated Studio user collection with explicit role templates:
  - website-admin
  - marketing-manager
  - editor
  - reviewer-publisher
  - seo-manager
  - analyst
  - auditor
- API-level access rules rather than UI-only role hiding.
- Versioned Pages collection with drafts, autosave, scheduled publishing, and retained versions.
- Editorial workflow state field from idea through refresh.
- Content brief fields for audience, visitor problem, intent, promise, evidence, primary CTA, secondary next step, owner, review date, conversion event, and approval requirements.
- Controlled block library for Hero, Feature Grid, Rich Text, CTA, and Form references.
- No arbitrary HTML or executable JavaScript block.
- Publish guard requiring a publishing role and an approved/scheduled editorial state before a draft transitions to published.
- Versioned Forms collection with a bounded field builder and optional consent-policy key references.
- Media collection with required alternative text, rights status, owner, expiry, and restricted internal notes.
- Anonymous content reads constrained to published Pages and approved Media.
- SEO fields for metadata title, description, canonical path, and indexability.
- Required database/secret configuration with no insecure production fallback.
- Focused role-policy tests.
- Dedicated CMS CI job using Node 24.15 and PostgreSQL.
- Generated Payload import map/types and local media are excluded from source control.

## Current publishing semantics

Payload draft/version functionality is the editorial storage layer. Publishing a Page or Form in CMS Studio is not yet equivalent to promoting a complete public website release.

A complete release still needs to freeze approved revisions and dependencies, build and verify a versioned static release, promote it without changing the current release on failure, verify delivery, and support rollback/takedown.

## Security and content boundaries

- Publishing permission is enforced in collection access and a before-change hook.
- Editors and SEO managers cannot update already-published records through the configured update filter.
- Ordinary public visitors are not granted CMS administration access.
- The visual builder exposes a fixed block schema rather than arbitrary executable content.
- Media rights approval controls anonymous reads, but quarantine, malware scanning, derivative generation, and private object storage are not implemented yet.
- No legal/privacy notices, retention periods, jurisdiction rules, customer testimonials, certifications, or unsupported business claims are generated by this CMS foundation.
